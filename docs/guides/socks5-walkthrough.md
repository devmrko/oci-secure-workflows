# SOCKS5로 사설 웹 화면 두 개 열기

이 절차의 목표는 내 PC의 브라우저에서 Public IP가 없는 개발 서버 두 곳의 웹 화면을 여는 것입니다. 터널 하나를 열어 둔 뒤 브라우저 주소만 바꿔 두 서비스를 오갑니다. 처음에는 사설 IP로 시험하고, 필요할 때 사설 도메인으로 확장합니다.

## 이번 예제에서 만들 접속 경로

다음 주소는 설명용입니다. 실제로 해당 위치에 웹 서비스가 실행 중이어야 합니다. 이 도구가 웹앱을 설치하거나 띄우는 것은 아닙니다.

```text
내 PC
 ├─ 브라우저
 └─ SOCKS5 프록시 127.0.0.1:1080
          │ SSH 터널
          ▼
      OCI Bastion
          ├─ 10.0.1.10:8080  개발 웹앱
          └─ 10.0.1.20:3000  별도 관리 화면
```

`127.0.0.1:1080`의 역할은 “어디에 연결할지 접수하는 곳”입니다. 브라우저가 `10.0.1.10:8080에 연결해 달라`고 요청하면 Bastion을 거쳐 그 서비스로 연결합니다. 다음 탭에서 `10.0.1.20:3000`을 열면 이번에는 그 목적지로 연결합니다.

## 1단계 준비된 환경인지 확인

[Bastion 준비](bastion.md)의 키·권한·client CIDR 설정을 먼저 완료합니다. Bastion의 FQDN/SOCKS5 기능이 활성화되어 있어야 하고 두 서버는 해당 Bastion이 접근할 수 있는 VCN과 네트워크 범위에 있어야 합니다.

이번 예제에서는 두 서버 각각의 방화벽에 필요한 포트를 허용해야 합니다.

| 구간 | 허용할 연결 |
|---|---|
| 개발자 PC → Bastion | PC의 실제 공인 출구 IP가 Bastion allowlist에 포함, outbound SSH 연결 가능 |
| Bastion → 개발 웹앱 | Bastion 사설 엔드포인트 IP에서 `10.0.1.10:8080`으로 TCP 연결 |
| Bastion → 관리 화면 | Bastion 사설 엔드포인트 IP에서 `10.0.1.20:3000`으로 TCP 연결 |

NSG·Security List뿐 아니라 서버 OS 방화벽과 앱의 listen 주소도 확인합니다. 프록시를 쓰더라도 닫힌 포트에 자동으로 접근할 수는 없습니다.

## 2단계 설정 파일에 Bastion 등록

저장소 루트 `oci-secure-workflows/` 디렉터리에서 실행합니다. 이미 실제 설정 파일이 있으면 복사 명령으로 덮어쓰지 말고 기존 파일을 편집합니다.

```sh
cp config/access.example.json config/access.json
```

`regions.ap-seoul-1`의 `bastion_id`, `public_key`, `private_key`를 실제 값으로 바꿉니다. `profile`은 해당 테넌시에 인증된 OCI CLI 프로파일 이름입니다.

예제 파일에는 아래 target이 이미 있습니다.

```json
"seoul-socks": {
  "region": "ap-seoul-1",
  "mode": "socks",
  "local_port": 1080
}
```

고정 포워딩과 달리 target에 `host`·`port`가 없습니다. 접속할 사설 서비스 주소를 나중에 브라우저가 알려 주기 때문입니다. 이 설정을 파일 전체와 바꾸는 것이 아니라 기존 `targets` 안의 항목으로 유지합니다.

## 3단계 터널 실행

```sh
python3 scripts/access.py plan seoul-socks
```

미리보기에 `Local endpoint: 127.0.0.1:1080 (socks)`와 `ssh ... -D 127.0.0.1:1080 ...`가 표시되는지 확인합니다. 아직 실제 연결은 없습니다.

```sh
python3 scripts/access.py connect seoul-socks --execute
```

이 명령은 세션을 만들고 ACTIVE 상태를 기다린 뒤 SSH를 실행합니다. 호스트키 확인·개인키 암호 입력이 요청되면 확인 절차를 진행합니다. SOCKS5용 사용자 이름과 비밀번호를 새로 만드는 과정은 없습니다. Bastion 세션은 SSH 키로 인증합니다.

SSH가 오류 없이 계속 실행되는 동안 터미널을 열어 둡니다. 일반 SSH처럼 서버 명령 프롬프트가 나오지 않아도 정상일 수 있습니다. 실제 연결 성공 여부는 다음 단계의 요청으로 확인합니다. `Session:` ID와 정리 명령도 표시됩니다.

## 4단계 브라우저보다 먼저 curl로 확인

다른 터미널에서 실제 웹 서비스의 경로에 맞춰 실행합니다. `/health`가 없는 서비스는 존재하는 경로를 사용합니다.

```sh
curl --connect-timeout 10 --max-time 20 \
  --noproxy '' --proxy socks5h://127.0.0.1:1080 \
  http://10.0.1.10:8080/health
```

- `--proxy`: 이번 요청은 지정한 중계기로 보내라는 뜻입니다.
- `socks5h://`: SOCKS5를 쓰고, 도메인 이름이 있으면 프록시 쪽에서 조회하도록 합니다.
- `127.0.0.1:1080`: 내 PC에서 실행 중인 중계기의 주소입니다.
- 마지막 URL: 최종적으로 연결할 **사설 웹서비스**입니다.
- `--noproxy ''`: 기존 `NO_PROXY` 환경 설정 때문에 이번 검증 요청이 프록시를 우회하지 않도록 합니다. 이 curl 실행 한 번에만 적용됩니다.

원래 서비스의 예상 응답이 오면 첫 경로가 연결된 것입니다. 401·403 응답이라면 웹서버까지 도달했을 수 있지만, 서비스 인증이나 권한 문제는 별도로 해결해야 합니다. 터널을 열었다고 서비스 로그인이 생략되지는 않습니다.

## 5단계 브라우저에 중계 주소 지정

브라우저별 프록시 설정 방식이 다릅니다. 여기서는 브라우저 자체의 연결 설정을 제공하는 Firefox를 예로 듭니다. 회사에서 관리하는 프록시 설정은 임의로 덮어쓰지 말고 허용된 개발용 환경을 사용합니다.

Firefox 설정에서 `프록시` 또는 `proxy`를 검색해 연결 설정 대화상자를 엽니다. 버전에 따라 메뉴 위치와 번역이 다를 수 있습니다. 수동 프록시 설정에서 다음 값을 입력합니다.

| 항목 | 입력 값 | 뜻 |
|---|---|---|
| 프록시 방식 | 수동 프록시 설정 | 중계 주소를 직접 지정 |
| SOCKS 호스트 | `127.0.0.1` | 내 PC의 중계기 |
| SOCKS 포트 | `1080` | 스크립트의 local_port |
| SOCKS 버전 | SOCKS v5 | 사용하는 중계 규약 |
| SOCKS v5 사용 시 DNS도 프록시로 조회 | 사설 도메인을 쓸 때 활성화 | 내부 이름 조회를 중계 경로로 처리 |

HTTP 프록시 입력칸에 `127.0.0.1:1080`을 넣는 것이 아니라 **SOCKS 입력칸**을 사용합니다. 다른 HTTP/HTTPS 프록시 값이 함께 남아 있으면 그 설정이 우선 적용될 수 있으므로 사용 중인 연결 설정을 확인합니다. 설정 전 값을 기록해 두어야 종료 후 원래 연결 방식으로 되돌릴 수 있습니다.

`프록시 사용 안 함 / No Proxy For`에 대상 IP나 도메인이 들어 있으면 해당 요청이 프록시를 우회합니다. 정책상 변경 가능한 환경에서 대상이 의도치 않게 우회되지 않는지 확인합니다. 일반 웹 탐색과 분리한 개발용 브라우저 환경을 쓰면 영향 범위를 이해하기 쉽습니다. [Firefox 연결 설정](https://support.mozilla.org/en-US/kb/connection-settings-firefox)

## 6단계 주소창에서 두 서비스를 열기

첫 번째 탭에 다음을 입력합니다.

```text
http://10.0.1.10:8080
```

두 번째 탭에는 다음을 입력합니다.

```text
http://10.0.1.20:3000
```

터널을 새로 만들거나 서버별 로컬 포트를 추가하지 않고 두 화면을 오갈 수 있습니다. 이 점이 여러 사설 서비스에서 SOCKS5를 사용하는 이유입니다. 단, 두 번째 서비스도 Bastion에서 접근 가능하고 방화벽이 허용되어 있어야 합니다.

주소창에 `http://127.0.0.1:1080`을 넣는 것은 잘못된 사용입니다. 그 주소는 최종 웹서비스가 아닙니다. 또한 curl에만 프록시를 지정했다면 브라우저 설정은 바뀌지 않습니다.

## 7단계 종료하고 원래 연결 방식으로 복구

1. 브라우저 프록시를 기록해 둔 원래 값으로 되돌립니다. 원래 회사 시스템 프록시를 사용했다면 그 설정으로 복구합니다.
2. 터널 터미널에서 `Ctrl+C`를 누릅니다.
3. 필요하면 실행 시 표시된 명령으로 OCI 세션을 삭제합니다. 로컬 터널 종료만으로 세션이 즉시 삭제되지는 않습니다.

프록시 설정을 남긴 채 터널만 끄면 브라우저가 계속 `127.0.0.1:1080`을 찾으므로 웹 접속이 실패할 수 있습니다. 세션 TTL이 만료됐을 때도 비슷한 증상이 납니다. 새 터널을 실행해도 기존 TCP 연결이 이어지는 것은 아니므로 화면이나 도구를 다시 연결해야 합니다.

## 어디에서 막혔는지 판단

| 증상 | 우선 확인 |
|---|---|
| localhost 1080 연결 거부 | 스크립트 터널 실행 여부, local_port 일치, SSH 오류 |
| 프록시에는 연결되지만 대상 응답이 없음 | 실제 서비스 실행, 사설 IP·포트, Bastion에서 대상까지 보안 규칙 |
| IP로는 되는데 사설 도메인으로는 안 됨 | 프록시 DNS 설정, VCN 내부 DNS에 이름 존재 여부 |
| curl은 되는데 브라우저는 안 됨 | 브라우저의 SOCKS 값, 우회 목록, 다른 프록시·관리 정책 |
| HTML은 뜨는데 일부 API·이미지만 실패 | 해당 요청의 실제 호스트·포트, localhost나 옛 Public IP를 가리키는 앱 설정, CORS |
| HTTPS 인증서 오류 | 접속 도메인과 인증서 일치, 신뢰 체인. 검증을 끄지 말고 원인 수정 |
| 일반 인터넷 페이지까지 안 열림 | 개발 브라우저의 모든 프록시 대상 요청이 Bastion으로 향하는지, VCN 외부 통신 가능 여부 |

이 절차는 본인의 사설 개발·관리 접속용입니다. 다른 사용자가 터널 설정 없이 웹서비스를 이용해야 한다면 [서비스 진입점 구성](infrastructure.md)을 사용합니다. [동적 포워딩의 서비스 범위](https://docs.oracle.com/en-us/iaas/Content/Bastion/Concepts/bastionoverview.htm), [curl SOCKS5 옵션](https://curl.se/docs/manpage.html).
